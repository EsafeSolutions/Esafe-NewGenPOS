## 1. Project at a glance

EsafePOS is a browser-based point-of-sale application for ERPNext and Frappe. It is delivered as a Frappe app named `esafepos`, with a Vue 3 single-page application served at `/pos`. It uses ERPNext's POS Profile, customer, item, stock, invoice, payment, and accounting records, and adds workflows for registers, promotions, returns, offline sales, outlet management, reporting, and stock counting.

| Area | Implementation |
|---|---|
| Server | Python, Frappe whitelisted APIs, ERPNext document APIs |
| Client | Vue 3, Vue Router hash routes, Pinia, Vite |
| Persistent business data | ERPNext invoices and stock/accounting documents plus EsafePOS DocTypes |
| Local/offline data | IndexedDB `esafepos`; service worker where supported; `esafepos-printing` stores workstation roles/intents, and the SDK owns its separate browser identity database |
| Supported framework line | Frappe / ERPNext 13 through 16; Python syntax remains compatible with 3.7 |
| Package | `esafepos`, app title `ESAFE POS` |
| License | AGPL-3.0-only; product name and logo are trademarks (see `license.txt` and `TRADEMARKS.md`) |

## 3. Architecture and request flow

```text
Browser
  /pos (Frappe page shell)
    └── Vue app (frontend/src)
         ├── Views and reusable components
         ├── Pinia stores: session, catalog, cart, help
         ├── API wrapper ───────────────┐
         ├── IndexedDB/offline queue     │
         └── Service worker (where supported)
                                        ▼
Frappe whitelisted endpoints (esafepos/api)
  ├── permission and outlet checks
  ├── promotion, pricing, currency, return and register rules
  └── ERPNext documents + EsafePOS DocTypes
        ├── POS Invoice / Sales Invoice / Payment Entry
        ├── POS Opening/Closing Entry, Stock Reconciliation
        └── register, audit, promotion, balance and workflow records
```

Typical startup calls `esafepos.api.session.get_bootstrap`, which supplies the selected POS Profile, register state, payments, currencies, settings, promotions, and catalog context. The client fetches/searches catalog data and updates the cart locally. On checkout, the client sends a sale request through `esafepos.api.sales`; the server validates the cashier's access, profile, current register, prices, promotions, serials, payment rules, and other enabled safeguards before creating the ERPNext invoice. The client receives the posted invoice/receipt and refreshes local stock and shift summaries.

### Important boundaries

- `esafepos/promotions/engine.py` is a pure Python rules engine. `frontend/src/promotions.js` mirrors it for immediate cart feedback. The server-side calculation is authoritative.
- ERPNext is the system of record for posted sales, returns, stock, and accounting. EsafePOS DocTypes retain workflow-specific state and audit details.
- `esafepos/public/pos/` is generated by Vite. Edit `frontend/src/` and rebuild; do not make source edits directly in generated output.
- ERPNext-version-sensitive behavior belongs behind `esafepos/erpnext_compat.py` where practical.

## 6. Persistent data model

Customer messaging adds `POS Customer Message` with a unique user/request identity and payload hash, customer/outlet/company, read-only text, channel/status, provider ID and invoice audit names stored as Data. Cashiers have owner-only read access and APIs enforce outlet scope. A pending record is committed before external submission; unknown outcomes are not retried automatically. EsafePOS Settings stores nonsecret `customer_messaging_config` JSON, `whatsapp_phone_number_id`, `whatsapp_api_version` and an encrypted native Password `whatsapp_access_token`. SMS continues to use ERPNext's own SMS Settings and sender-role policy. Images are transient browser/transport data rather than public File records. Site migration is required.

ERPNext standard documents remain central: `POS Invoice`, `Sales Invoice`, `Purchase Invoice`, `Supplier`, `POS Opening Entry`, `POS Closing Entry`, `Payment Entry`, `Stock Reconciliation`, `Stock Entry`, `Sales Order`, `Customer`, `Item`, and their standard child records. EsafePOS's DocTypes provide configuration and POS-specific workflow state.

The item/stock manager uses `Item.disabled`, native sale/purchase flags, `Item Attribute`/attribute values and template/variant child rows. Inventory remains in `Bin` and `Stock Ledger Entry`; transfers are submitted `Stock Entry` Material Transfers, and adjustments/counts use `Stock Reconciliation`. Transfer request identities become deterministic `POS-TRF-…` native names, with a payload fingerprint and reason in remarks; no parallel inventory ledger or custom transfer table is added. The capability selectors add **Transfer warehouse stock**, and repeatable setup grants native inventory/item rights to EsafePOS Manager.

Receiving uses native Material Receipt `Stock Entry` rows and deterministic `POS-RCV-…` names, with the reason and request fingerprint in remarks. **Receive warehouse stock** is a separate capability. Live sync stores only a random committed-change marker in Frappe's site cache; authoritative prices, quantities, reservations and conversions continue to come from ERPNext tables. Browser-tab storage retains uncertain receipt identities, and IndexedDB patches current loaded item rows without clearing other cached items or queued sales.

Buying uses native Purchase Invoice items/taxes and Payment Entry references. Supplier balances aggregate permitted, uncancelled company `GL Entry` credits minus debits. Supplier, Purchase Invoice and Payment Entry carry unique `esafepos_buying_key` and request fingerprint `esafepos_buying_hash`; invoices/payments retain `esafepos_buying_profile`, and payments retain `esafepos_supplier_payment_method`. The settings DocType adds `enable_buying`; both capability selectors include **Manage buying and suppliers**. Migration installs these fields; no additional balance ledger is created.

Invoice scanning adds `purchase_ocr_enabled` (default off), `purchase_ocr_gemini_key` (encrypted Password), and `purchase_ocr_model` (default `gemini-3.5-flash-lite`) to EsafePOS Settings. Extracted files/data are transient; the scanner creates no invoice, File or extra ledger. Native tax rows distinguish `Total` tax from `Valuation and Total` expenses. `erpnext_compat.sum_fields` selects the supported aggregate syntax while retaining GL read/user permissions.

Customer pricing uses the native `Customer.default_price_list` link to ERPNext `Price List` and its `Item Price` records. Assignments are shared across outlets; the POS validates the sale currency before offering a list. Customer balance filters aggregate uncancelled `GL Entry` debits minus credits in company currency. Activity filters use Customer creation timestamps or submitted POS/Sales Invoice posting dates and the existing receipt-customer attribution field. No additional persistent schema is introduced.

Saved change uses standard `Loyalty Point Entry` records linked to a funding `Journal Entry`. Both invoice types carry `esafepos_loyalty_change_amount` and `esafepos_loyalty_change_entry`; register cash-in rows carry `loyalty_change_entry`. Migrations install the read-only invoice references. ERPNext's invoice change and consolidation remain unchanged; physical change is calculated for POS receipts after deducting funded points.

## 7. Feature lifecycle and integrity rules

1. **Authorize before acting.** Resolve the user and POS Profile, then apply role/capability, company, outlet, register ownership, and ERPNext DocType permission checks.
2. **Quote from current context.** Resolve delivery-app pricing, the customer's assigned selling list, then outlet/group pricing; use the sale currency and active shift rates. Missing customer/app item rates fall back to the outlet list.
3. **Treat local calculations as provisional.** Cart calculations improve speed and clarity; server submission repeats checks against current ERPNext state.
4. **Post using ERPNext documents.** Sales and returns flow through ERPNext invoice documents; stock and accounting changes are handled by ERPNext posting.
5. **Record POS workflow state and audit.** Shift ownership, expected cash, approvals, promotion detail, and operational events are held in EsafePOS records.
6. **Make offline retries safe.** Queue stable sale payloads with identifiers, serialize uploads where possible, and recognize duplicate submissions by idempotency key.
7. **Respect asynchronous close.** Consolidation may retry; a failed/unfinished close must remain diagnosable and recoverable rather than silently disappearing.

## 9. Build, development, and verification

From the repository root:

```powershell
cd frontend
npm ci
npm run dev
```

The development server runs Vite on port 8080 and proxies API calls to a local Frappe bench on port 8000. Build committed production assets with:

```powershell
cd frontend
npm run build
```

Focused repository checks:

```powershell
python -m unittest esafepos.promotions.test_engine
python scripts/test_shift_schedule.py
cd frontend
node parity-check.mjs
node barcode-check.mjs
node clock-check.mjs
```

Run the parity check when changing either promotion evaluator; run barcode/clock checks when changing those utilities. For UI changes, follow repository guidance to build and capture desktop/mobile screenshots. Do not edit `esafepos/public/pos/` by hand.
